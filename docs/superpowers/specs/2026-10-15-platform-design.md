- 作成日：2026-10-15
- 状態：レビュー待ち
- 対象：全体設計（実装計画はフェーズごとに別文書で作る）

## 0. 目的と前提

### 0.1 何を作るか

コードを渡せば、ビルドからデプロイ、公開までを自動で行う **一般公開の PaaS**。静的サイトも動的アプリ（Node / Python / PHP など、Docker コンテナならなんでも）も動かせる。レンタルサーバーのように「場所を貸すだけ」のサービスではない。

### 0.2 誰のためか

- **学生（中学生・高校生・専門学校生・高専生・大学生・大学院生）**：審査を通れば、ベースプランを無料で使える
- **初めて個人開発をする人**：手動審査を通れば、Pro プランを一定期間無料で使える（Starter Grant）
- **それ以外の人**：有料（Pro）プランを使う

### 0.3 成功の基準

1. 学生が、GitHub への push、CLI、Web アップロードのどれでも、`https://<アプリ名>.<アプリ用ドメイン>` でサイトやアプリを公開できる
2. 本人が自分で申し込まない限り、**課金は一切発生しない**
3. 個人情報は「持たない・読めない・残さない」を守る
4. 運営者 1 人で回せる（自動化を優先する）
5. Mac と Ubuntu の両方で、同じ手順で開発環境が動く

### 0.4 仮の名前

| 用途 | 仮の名前 | 決める時期 |
|---|---|---|
| 本体（画面・API） | `example.com` | フェーズ 8 |
| 利用者のアプリ | `examplepage.com` | フェーズ 8 |
| CLI コマンド | `yourservice` | フェーズ 8 |

名前は設定ファイルの 1 か所で変えられるようにする。

## 1. 全体の構成

### 1.1 方式

自前の本体（TypeScript）と、Kubernetes の標準的な部品を組み合わせる。どこでも同じ構成で動くようにする。

| 環境 | Kubernetes |
|---|---|
| 開発（Mac / Ubuntu） | k3d（Docker の中で k3s を動かす） |
| 最初の本番 | クラウドのマネージド Kubernetes（会社はフェーズ 8 で決める） |
| 将来の本番 | 自前のサーバー（k3s / Talos Linux） |

クラウド独自のサービス（Cloud Run など）には依存しない。

### 1.2 部品

```
┌──────────── example.com（本体クラスタ）────────────┐
│  Web 画面 (Next.js)   CLI   スマホアプリ (Expo)        │
│              └──────┬──────┘                         │
│                     ▼                                │
│               API サーバー                            │
│   アカウント / チーム / アプリ / 審査 / 付与 / 課金 / 計測 │
│        │             │              │                │
│   PostgreSQL     ジョブキュー     ストレージ(S3 互換)     │
│   (本体用)        (pg-boss)                           │
│   個人情報 DB（分離）                                   │
│                                                      │
│   管理画面 (apps/admin) ← Tailscale からのみ            │
└──────────────────┬───────────────────────────────────┘
                   │
┌──────────── 利用者クラスタ ──────────────────────────┐
│  ビルドワーカー（隔離）→ 内部レジストリ（署名つき）        │
│  Traefik → *.examplepage.com                         │
│  静的サイト配信サーバー（共通）                          │
│  利用者の動的アプリ（gVisor、ユーザーごとの名前空間）       │
│  利用者の DB（CloudNativePG）                          │
└──────────────────────────────────────────────────────┘
```

| 部品 | 役割 |
|---|---|
| Web 画面 | ログイン、アプリ・チームの管理、デプロイ状況とログ、学生証の提出、プラン変更 |
| CLI | `yourservice deploy` などの操作 |
| スマホアプリ | 管理と通知（フェーズ 9） |
| API サーバー | **すべての操作の唯一の窓口**。無料枠・停止・課金のルールはここに集める |
| 管理画面 | 運営者専用。別のアプリで、インターネットに公開しない |
| PostgreSQL（本体用） | ユーザー、チーム、アプリ、デプロイ、利用量、付与 |
| 個人情報 DB | 学生証の暗号文、保護者の同意記録など。管理画面だけがアクセスできる |
| ジョブキュー | ビルド、停止・再開、月初・年度のリセット、削除の期限処理 |
| ストレージ | ソースの tar.gz、ビルドログ、静的サイトのファイル、バックアップ |
| ビルドワーカー | ソースをコンテナイメージ（または静的ファイル）に変換する |
| Traefik | サブドメインごとに振り分ける。ブロックもここで行う |
| 静的サイト配信サーバー | ストレージ上のファイルを、複数のサイト分まとめて配る |

### 1.3 決まり

- Kubernetes を直接操作するのは **API サーバーとワーカーだけ**。画面・CLI・スマホアプリは必ず API を通す
- 本体クラスタと利用者クラスタは分ける。開発環境でも k3d で 2 つのクラスタを作る
- ジョブキューは PostgreSQL の上で動く pg-boss を使い、Redis は使わない

### 1.4 リポジトリの構成（モノレポ）

```
apps/web        利用者向けの Web 画面（Next.js）
apps/api        API サーバー
apps/admin      運営者用の管理画面（別に配置する）
apps/cli        CLI
apps/builder    ビルドワーカー
apps/static     静的サイト配信サーバー
apps/upload     学生証アップロード専用の小さな画面
apps/mobile     スマホアプリ（Expo）
packages/shared 共通の型、ルール、プランの定義
packages/i18n   日本語・英語の文言
infra/          k3d・本番の Kubernetes マニフェスト（GitOps）
docs/           設計書、手順書、チェックリスト
```

### 1.5 言語と主な技術

- 言語：TypeScript
- 画面：Next.js
- API：Node.js（Hono または Fastify）
- スマホ：React Native（Expo）
- 表示言語：**日本語と英語**（画面・メール・通知のすべて）

## 2. アカウント、チーム、ログイン

### 2.1 アカウント

- 集める情報：メールアドレス、表示名（ニックネーム）、言語
- **集めない情報**：本名、住所、電話番号、パスワード
- 生年月日は登録時に入力するが、**保存しない**。年齢を判定して、「13 歳以上である」ことと「18 歳になる年月」だけを残す
- 13 歳未満は登録できない

### 2.2 ログイン（パスワードなし）

| 方法 | 内容 |
|---|---|
| パスキー | おすすめとして案内する |
| メール | 1 回きりのコードまたはリンク。数分で失効する |

- GitHub / Google でのログインはしない。GitHub は「リポジトリをつなぐ」ためだけに使う
- **別の端末でメールのリンクが押された場合**：
  1. ログインを要求した端末に、QR コードと 2 桁の数字を表示する
  2. リンクを押した端末で QR を読み取る
  3. その端末に、3 つの数字の候補と「どこからのログインか（端末・おおよその地域）」を表示する
  4. 同じ数字を選ぶとログインが完了する（QRLJacking 対策）
- ログイン中の端末一覧を表示し、強制ログアウトができる。それ以外のセッション管理は利用者に任せる

### 2.3 アカウントの復旧

1. 復旧フォームから申請する（管理者のメールに届く）
2. 利用者が復旧コードを入力する
3. コードが正しければ、管理者が最終確認して復旧する
4. 使った復旧コードは無効にし、新しいコードを 1 つ発行する

**復旧コード**：

- 1 人 1 つ。登録時に一度だけ表示する
- 16 文字。大文字、小文字、数字、記号、ひらがな、カタカナ、漢字を使う
- 紛らわしい文字（`口`/`ロ`、`力`/`カ`、`一`/`ー`、`O`/`0`、`l`/`1` など）を除いたリストから作る
- 入力時に Unicode の正規化（NFKC）で、全角・半角などをそろえる
- サーバーにはハッシュ値（Argon2id）だけを保存する

### 2.4 チーム

| 項目 | 内容 |
|---|---|
| 作成 | 誰でも作れる。メンバーはメールで招待する |
| 役割 | オーナー（1 人。課金・削除）、管理者（招待・設定）、メンバー（デプロイ・ログ） |
| 人数 | 最大 10 人 |
| アプリの持ち主 | 個人またはチーム |
| 無料枠 | チームのアプリは、**オーナーの枠**を使う。個人の枠とチームの枠は共有する |
| オーナーの引き継ぎ | オーナーは他のメンバーに引き継げる。引き継がなければ、オーナーの状態に従って停止ルールが適用される |

データの持ち方では、「枠を持つのはアカウント」「アプリを持つのは個人かチーム」を分ける。

### 2.5 アクセス履歴

- 本人は、自分のログイン履歴（日時、端末、おおよその地域、方法）を見られる
- 知らない端末からのログインは通知する

## 3. デプロイ

### 3.1 流れ

```
GitHub に push ─┐
CLI deploy ─────┼→ ① ソースを tar.gz にしてストレージに保存（状態：待機中）
Web アップロード ┘
                    ② ビルドワーカーが受け取る（状態：ビルド中）
                       ・秘密情報チェック（gitleaks）
                       ・Dockerfile あり → BuildKit（ルートレス）
                       ・Dockerfile なし → Cloud Native Buildpacks
                       ・静的サイト → ビルド結果のファイルを取り出す
                       ・脆弱性・マルウェアのスキャン（Trivy、ClamAV）
                    ③ 動的：イメージに署名して内部レジストリへ
                       静的：ファイルをストレージへ
                    ④ 動的：Kubernetes に反映（状態：起動中）
                       ヘルスチェックに通ってから通信を切り替える
                    ⑤ 公開（状態：稼働中）
```

### 3.2 入口

| 入口 | 内容 |
|---|---|
| GitHub | GitHub App（権限は「コードを読む」だけ）。選んだブランチへの push で自動デプロイ。Webhook は署名を検証する |
| CLI | 現在のフォルダを圧縮して送る。`.gitignore` に従い、`.env` と `.git/` は常に除外する |
| Web | ZIP をアップロードする。`.env` と `.git/` は取り除く |

### 3.3 決まり

| 項目 | 内容 |
|---|---|
| アプリの種類 | 作成時に「静的サイト」か「動的アプリ」を選ぶ |
| 環境変数 | 画面・CLI で設定する。暗号化して保存し、起動時にだけ渡す |
| 失敗したとき | 前のバージョンが動き続ける。理由はログで見られる |
| ロールバック | 過去に成功したデプロイを選んで戻せる |
| ビルド時間 | 上限 15 分 |
| 秘密情報が見つかったら | 公開を止め、環境変数に移すよう案内する |
| 実行ファイル・大きな圧縮ファイル | `.exe`、`.apk`、`.dmg` などを含むデプロイは、公開前に保留して運営者が確認する |

### 3.4 静的サイトの配信

- 静的サイトはコンテナで動かさず、共通の配信サーバーがストレージ上のファイルを返す
- `.env`、`.git/`、`.DS_Store` などのドットで始まるファイルは、常に 404 を返す
- 前に CDN（Cloudflare）を置く

### 3.5 サブドメイン

- `https://<アプリ名>.examplepage.com`
- ワイルドカード DNS と、ワイルドカード証明書（Let's Encrypt の DNS-01 認証、cert-manager）を使う
- `login`、`admin`、`www`、`paypal` など、予約語と有名ブランド名は使えない
- `examplepage.com` は Public Suffix List に登録申請する

### 3.6 アクセスログ

- アプリの持ち主は、日時、ページ、ステータス、ブラウザの種類、参照元を見られる
- 閲覧者の IP は一部を伏せて表示する（例：`203.0.113.xxx`）
- 30 日で削除する

## 4. データベース（利用者向け）

| 項目 | 内容 |
|---|---|
| 仕組み | CloudNativePG。動的アプリ 1 つにつき DB 1 つ |
| 使い方 | 画面で「DB を追加」を押すと、`DATABASE_URL` が自動でアプリに渡る |
| 隔離 | アプリごとに別の DB・別のユーザー。ネットワーク上も、そのアプリからしかつながらない |
| 暗号化 | 保存データとバックアップを暗号化する |
| バックアップ | 常に自動で保存。過去 7 日間の好きな時点に、利用者が自分で戻せる |
| 障害 | 予備に自動で切り替える |
| 外部からの接続 | 原則できない。CLI 経由の一時的なトンネルだけ |
| 容量の上限 | 80% で通知、100% で書き込みだけ停止する（読み取りは続けられる） |
| 責任 | アプリが集めたデータの管理責任はアプリの持ち主にあると、利用規約に書く。個人情報の扱い方ガイドを用意する |

## 5. プラン、付与、制限

### 5.1 プラン

| プラン | 対象 | 料金 |
|---|---|---|
| なし | 学生でなく、未契約の人 | アカウントだけ作れる。アプリは動かせない |
| Student | 審査済みの学生 | 無料 |
| Pro | 誰でも（18 歳未満は保護者の同意が必要） | 有料（値段と中身はフェーズ 7 で決める） |

### 5.2 Student プランの初期値

| 項目 | 値 |
|---|---|
| 動的アプリ | 1 つ、メモリ 512MB、CPU は低め |
| 動的アプリの稼働時間 | **月 240 時間、年度（4/1〜3/31）2,000 時間** |
| スリープ | 15 分アクセスがなければスリープ。スリープ中は時間を数えない |
| 静的サイト | 1 つ、稼働時間は無制限 |
| 静的サイトの容量 | 200MB（1 ファイルは最大 25MB） |
| 転送量 | 静的サイト・動的アプリそれぞれ月 10GB |
| DB | 1 つ、256MB、接続数は最大 10 |

すべての数字は、管理画面か設定で変えられるようにする。

### 5.3 稼働時間の数え方

- 1 分ごとに、動いているコンテナの数を記録する（生の記録を残す）
- コンテナ 1 つが 1 時間動いたら「1 時間」と数える

### 5.4 上限に達したとき

| 状況 | 動作 |
|---|---|
| 80% | メール、画面、スマホに通知 |
| 月の稼働時間の上限 | 月末まで動的アプリを停止し、翌月 1 日に自動で再開 |
| 年度の稼働時間の上限 | 3 月 31 日まで停止 |
| 転送量の上限 | 月末までブロック。閲覧者には「今月の転送量の上限に達しました」と表示（HTTP 503）。翌月 1 日に再開 |
| 容量の上限 | 超えるデプロイはビルド時に失敗させる。公開中のものはそのまま |
| 停止中 | 設定・データ・イメージは残す。本人が Pro に申し込めば、すぐに再開 |

**自動課金はしない**。有料プランへの切り替えは、必ず本人の操作で行う。

### 5.5 付与（Grant）

無料での利用や上乗せは、すべて「付与」という 1 つの仕組みで扱う。

```
付与 = { 対象（アカウントまたはアプリ）, 種類, 内容, 開始日, 終了日, 理由, 承認者 }
```

| 種類 | 内容 |
|---|---|
| Student | 学生審査の承認で付与。有効期限は 3 月 31 日、停止日は 4 月 30 日 |
| Starter Grant | 初めての個人開発者向け。Pro を無料にする。期間は運営者が審査時に決める。1 人 1 回だけ |
| イベントブースト | 学園祭などの期間だけ上限を引き上げる |

**Starter Grant**：

- 申請フォーム：作りたいもの、GitHub アカウント、自己紹介
- 不正対策：メール認証、GitHub アカウントの作成日の確認、必要なら SMS 認証（番号はハッシュ化して重複確認にだけ使う）
- 終了の 14 日前と 3 日前に通知する。終了後は自動課金しない。申し込みがなければ停止する（データは残す）

**イベントブースト**：

- 利用者が申請する：イベント名、日付（最大 7 日間）、予想アクセス数
- 開始の 3 日前までに申請する。運営者が承認し、上げ幅を調整する
- 期間中：転送量の上限を引き上げ、スリープをオフにし、メモリを増やし、異常検知のアクセス急増の基準を緩める
- 学生は無料。使った稼働時間は月・年の上限に数える
- 期間が終わったら自動で元に戻る

### 5.6 状態の変化

利用の状態（有効 / 猶予中 / 停止中 / ブロック中 / 凍結）の変化は、**1 か所の状態遷移として書く**。年度の切り替え、月初のリセット、Pro への申し込み、付与の期限が重なっても、矛盾が出ないようにする。「認証の有効期限」と「停止する日」は別々の日付として持つ。

## 6. 学生審査

### 6.1 流れ

```
学生証を提出 → 審査待ち → 承認（Student の付与）
                       → 差し戻し（理由を通知、再提出できる）
```

- 提出するもの：学生証の画像、学校名、学校の種類、**卒業（修了）予定年**
- 運営者は管理画面で審査する
- 審査の部分は差し替えられる作りにし、将来 SheerID などに切り替えられるようにする

### 6.2 年間スケジュール

| 時期 | 状態 |
|---|---|
| 3 月 1 日〜 | 翌年度の再登録の受付を開始。卒業予定年を過ぎた人には案内を送る |
| 3 月 31 日 | 認証の有効期限 |
| 4 月 1 日〜4 月 30 日 | 猶予期間。無料のアプリは動き続ける |
| 5 月 1 日 | 再登録していない人の無料アプリを停止（データは残し、再登録で再開） |

審査ルール：3 月の提出では、卒業予定年で翌年度も在学しているかを判定する。4 月以降は新年度の学生証か在学証明書を求める。

### 6.3 学生証の保護（持たない・読めない・残さない）

- 学生証の提出は、**専用の小さな画面（`apps/upload`）からだけ**行う。メールでは受け付けない。利用規約に「運営がメールで学生証を求めることはない」と書く
- 画像は**利用者のブラウザ内で暗号化**してから送る
  - 方式：X25519 と ML-KEM（耐量子）を組み合わせたハイブリッド方式で鍵を共有し、本体は AES-256-GCM で暗号化する
  - 運営者の公開鍵で暗号化する。秘密鍵は運営者の YubiKey の中にだけある
  - YubiKey は 2 本用意し、両方に鍵を登録する（1 本は保管用）
- サーバー、DB、バックアップが盗まれても、学生証は読めない
- 審査が終わったら**すぐに削除**する。7 日以内に審査されなかったものも自動で削除し、再提出をお願いする
- 学生証は**バックアップに含めない**
- 残すのは「承認済み、学校の種類、卒業予定年、有効期限」だけ
- アップロード画面は Subresource Integrity と厳しい CSP で改ざんを防ぐ

## 7. 課金

| 経路 | 内容 |
|---|---|
| Web | Stripe の決済ページ（カード番号はこちらのサーバーを通らない） |
| スマホアプリ | App Store / Google Play のアプリ内課金（フェーズ 9） |
| 後で追加 | コンビニ払いなど |

- どの経路で払っても、内部では「Pro が有効」という 1 つの状態にまとめる
- Stripe、App Store、Google Play からの通知は、必ず署名を検証する
- **18 歳未満が Pro に申し込むとき**は、保護者のメールに同意の確認を送り、承認されてから決済に進む。同意が済んだら保護者のメールは削除し、「同意済み」の記録だけ残す
- 値段と Pro の中身はフェーズ 7 で決める

## 8. 通知

イベントが起きたら、メール、Web、スマホの通知先に配る**通知の部品を 1 つ**作る。

| 通知 | 相手 |
|---|---|
| デプロイの成功・失敗 | 利用者 |
| 上限の 80%・到達 | 利用者 |
| 異常によるブロック | 利用者と運営者 |
| 審査の結果、学生認証の更新案内、付与の終了予告 | 利用者 |
| 知らない端末からのログイン | 利用者 |
| ハニートークンの作動、証明書の発行、DNS の変更 | 運営者（最優先） |

- 本番のメール送信：Amazon SES または Resend（フェーズ 8 で選ぶ）
- 開発中のメール：Mailpit
- 送信ドメイン認証：SPF、DKIM、DMARC（`p=reject`）、MTA-STS

## 9. セキュリティ

考え方：**突破されることを前提にし（侵害前提）、何重もの壁で被害を止める（多層防御）**。人がいなくても自分を守れる仕組みを優先する。

### 9.1 第 1 層：堀（外からの攻撃）

- Cloudflare：DDoS の吸収、WAF、サーバーの IP を隠す
- サーバーへの直接アクセスは禁止し、Cloudflare Tunnel 経由だけにする
- SSH を使わない
- アプリごとに回数制限をかける。API にも回数制限をかける
- `/.env`、`/.git/config`、`/wp-admin` などを探して回る IP は自動でブロックする

### 9.2 第 2 層：城壁（区画の分離）

- 利用者のコンテナは gVisor で隔離する。将来、Kata Containers / Firecracker のマイクロ VM に差し替えられるようにする
- ユーザーごとに名前空間を分ける
- ネットワーク：他のユーザー、本体、クラウドの管理用アドレス（`169.254.169.254`）には通信できない。ポート 25 は禁止
- CPU、メモリ、ディスク、プロセス数に上限をかける。特権コンテナは禁止
- 外への通信量と接続数にも上限をかける。急に増えたら自動でブロックする
- ノードを「学生のアプリ」「有料のアプリ」「ビルド」に分ける
- 利用者のアプリが動くノードは、数日ごとに作り直す
- OS は Talos Linux（読み取り専用、シェルなし）
- ビルドワーカーもアプリと同じルールで隔離する

### 9.3 第 3 層：城門（ゼロトラスト）

- 内部の通信もすべて mTLS で暗号化し、お互いを認証する（Cilium）
- 長く使える鍵を置かない。一時的な認証情報だけを使う（Workload Identity / Vault）
- 本番環境に `.env` ファイルを置かない
- 本体の DB は Row Level Security で「自分のデータしか読めない」を強制する
- 個人情報は別の DB に入れる。利用者向けの API はその DB に接続する権限を持たない
- 暗号化の鍵は KMS で管理し、学生証用には専用の鍵を使う

### 9.4 第 4 層：見張り

**自動ブロック**：

```
異常を検知 → そのアプリへのアクセスを即座にブロック
           → 閲覧者には「このサイトは一時停止中です」と表示
           → 利用者に通知（理由と異議申し立ての方法）
           → 運営者に通知（管理画面へのリンク付き）
           → 運営者が解除、または停止の継続・凍結
```

| 深刻さ | 例 | 自動でやること |
|---|---|---|
| 高 | マイニング、コンテナからの脱出の試み、フィッシングの判定 | ブロックとコンテナの停止 |
| 中 | ファイル配布の疑い、急な転送量の増加 | ブロック |
| 低 | CPU がやや高い状態が続く | 運営者に通知 |

「止める」はブロック（Traefik で遮断）、停止（コンテナを 0 にする）、凍結（アカウントごと）の 3 段階にする。

**検知のしくみ**：

- Falco（コンテナ内の怪しい動き）
- CPU 使用率（マイニング）
- Google Safe Browsing（公開時のフィッシング判定）
- ファイル配布：転送量が 1 つのファイルに集中している、外部から直リンクされている
- 全ページに通報リンクを置く
- 外への通信をプロキシ経由にして記録する

**ハニートークン（罠）**：

| 罠 | 置き場所 |
|---|---|
| 偽のクラウド鍵 | 設定ファイル、環境変数、コンテナの中 |
| 偽の管理者アカウント | 本体 DB のユーザー一覧 |
| 偽の学生データ | 個人情報 DB |
| 偽の API キー | リポジトリの奥、バックアップの中 |
| 偽の内部 URL | 管理画面への「隠しリンク」風のページ |
| `example.com/.env` | 偽の鍵が書かれたファイルを返す |
| 偽のパスワードログイン画面（`/admin/login` など） | このサービスにはパスワードがないので、入力した時点で攻撃者と判断する |

罠が作動したら、その IP やアカウントを即ブロックし、運営者に最優先で通知し、記録を保存する。罠の中身は本番の構築時に生成し、リポジトリには書かない。

**記録**：操作記録は、一度書いたら消せないストレージ（Object Lock）に保存する。

### 9.5 第 5 層：本丸（運営者）

- 管理画面は別のアプリで、**Tailscale 経由でしか入れない**。パスキーまたは YubiKey が必須
- 審査・停止・凍結などの操作は、誰が・いつ・何をしたかをすべて記録する
- YubiKey を 2 本用意し、GitHub、クラウド、Stripe、レジストラ、Tailscale のすべてに登録する
- 危険な操作（全データ削除、本番の鍵の変更など）は 24 時間前に予約し、通知が来るようにする
- インフラの変更は Git 経由だけ（Argo CD による GitOps）。直接の変更は自動で元に戻し、通知する

### 9.6 第 6 層：兵站（自分のコード）

- 依存パッケージのバージョンを固定し、Renovate で更新する
- 本体のイメージにも署名し、Kubernetes では署名されたイメージだけを起動する
- CI で静的解析、秘密情報の混入、脆弱性、ファズテストを行う
- 機能ごとに脅威モデリング（STRIDE）を行う
- セキュリティのテスト（他人のデータが見えない、ブロックが効く、罠が作動する、など）を自動テストとして書く

### 9.7 第 7 層：再建

- 削除も上書きもできないバックアップを、別のクラウドに保存する
- 月に 1 回、実際に復元してみる
- 公開前に外部の脆弱性診断を受ける。利用者が増えたらバグバウンティを検討する
- 緊急時の手順書（乗っ取り、情報の漏えい）を用意する
- `security.txt` を置いて、脆弱性の報告を受け付ける

### 9.8 VPN の扱い

検知には、IP の情報データベース（MaxMind / IPinfo）、Tor の出口ノードの一覧、Cloudflare のボット判定を使う。

| 場所 | 扱い |
|---|---|
| 学校のネットワーク、iCloud プライベートリレー | 常に許可（例外リスト） |
| 新規登録、学生証の提出 | VPN・プロキシ・Tor を検知したら一律ブロック |
| Pro への申し込み（Web） | VPN をブロック |
| Pro への申し込み（App Store / Google Play） | 許可 |
| サイトの変更・閲覧 | ブロックしない。不正を検知したら自動ブロック |
| 管理画面 | Tailscale 以外はつながらない |

### 9.9 ドメインの保護（ドメイン取得時のチェックリスト）

1. レジストリロックに対応したレジストラを選ぶ（Cloudflare Registrar など）
2. レジストラのアカウントは、普段とは別のメールアドレスで作り、YubiKey を必須にする
3. 10 年分を登録し、自動更新を有効にし、支払い方法を 2 つ登録する
4. レジストリロックをかける
5. DNSSEC を有効にする
6. CAA レコードで、認証局と自分の契約アカウントを指定する
7. CT ログを監視し、証明書が発行されたら通知する
8. HSTS プリロードに登録する
9. SPF、DKIM、DMARC（`p=reject`）、MTA-STS を設定する
10. 紛らわしいドメインを取得し、他人が取ったら通知されるようにする
11. NS と WHOIS の変更を監視する
12. `examplepage.com` を Public Suffix List に登録申請する

### 9.10 個人情報のまとめ

| 情報 | 扱い |
|---|---|
| クレジットカード | 触らない（Stripe / ストア） |
| 本名、住所、電話番号 | 集めない（電話番号は SMS 認証のときだけ、ハッシュ値を保存） |
| 生年月日 | 保存しない（判定結果だけを残す） |
| メールアドレス | 暗号化して保存する。照合には別のハッシュ値を使う |
| 学生証 | ブラウザ内で暗号化し、審査後すぐ削除する |
| 保護者のメール | 同意の確認が終わったら削除する |
| アクセスログの IP | 一部を伏せ、30 日で削除する |
| 退会した人のデータ | 30 日で完全に削除する |
| ログ全般 | 個人情報が混ざらないよう、自動で伏せる |
