## 指摘

### 高: PII DB は apps/api の別コンテナからホスト公開ポート経由で到達できる

- **場所:** `dev/compose.yaml:66-69`、`packages/platform/src/pii/ingest.ts:14-17`、`apps/upload/src/main.ts:14-15`
- **何が起きるか:** PII DB は `127.0.0.1:54321` に公開されており、そのポート公開は `ys-piinet` 外の Docker コンテナからホスト経由で到達可能になる。台帳もコンテナ IP 直指定で届くと認識している。したがって「apps/api コンテナから届かない」というネットワーク分離は保証されない。API コンテナにDB資格情報がないため通常のコード経路では接続しないが、API侵害時のネットワーク到達性そのものは遮断されていない。実際の到達性はこのレビューでは実環境で試していない。
- **確度:** 高（公開ポートの設定・台帳の明記。実環境到達の再現は未実施）

### 高: 二つの DB の処理は原子的でなく、応答喪失時に審査記録が食い違う

- **場所:** `apps/api/src/verification/review.ts:98-115,134-146`、`packages/platform/src/pii/store.ts:33-41`
- **何が起きるか:** 本体 DB トランザクション内でステータスと Grant を更新した後、PII DB 側で審査記録を追加して暗号文を消す。PII 側コミットが成功した直後に接続断等で呼び出し側が失敗扱いになると、本体 DB はロールバックする一方、PII 側は審査済み記録と削除が確定する。再試行では暗号文がなく `no_submission` / `delete_failed` となり、再提出まで審査が進められない。削除失敗そのものは PII 側トランザクションでロールバックされるが、成功後の応答喪失を跨ぐ分散原子性はない。承認でも差し戻しでも起こり得る。
- **確度:** 高（明示的に別々のトランザクションを使用。障害タイミングはコード経路からの推論）

### 中: 期限切れ処理で暗号文が消えた後、本体DBのコミットだけ失敗すると pending のまま復旧不能になり得る

- **場所:** `apps/api/src/verification/purge.ts:38-46`
- **何が起きるか:** 本体 DB の `expired` 更新は未コミットのまま、別 DB の暗号文削除を実行する。削除が成功した後に本体 DB のコミットが失敗すると、暗号文なし・本体状態 `pending` が残る。7日経過済みなので同じ期限切れ処理は再実行されるが、`deleteBlobs` は0件削除でも成功扱いになり `expired` へ移せるため自動再試行は可能。ただし再試行まで一時的に審査待ち表示と実体が食い違う。
- **確度:** 中（コミット障害の順序に依存）

### 中: 一部の有効な IPv4-mapped IPv6 アドレスが Tailscale 範囲として誤認される

- **場所:** `apps/api/src/admin/tailscale.ts:21-24,49-65`
- **何が起きるか:** IPv4末尾を含むIPv6を解析すると仮IPv4グループを作った後、`::` 圧縮を含む場合はそのグループ数を使ってゼロ埋めし、最後に先頭6グループを IPv4 値に置換する。例えば `::ffff:100.64.0.1` は途中のグループ数が8を超えて拒否されるため false negative となる。IPv4-mapped が誤って許可される形ではないので、通常は管理API迂回ではなく、プロキシやランタイムがソケット元をこの表記で渡す環境で正当な管理者が拒否される問題。
- **確度:** 中（パーサーの手計算。実行テストは未実施）

### 中: Grant の取り消し・手動状態変更時に状態遷移を呼ぶ接続箇所がない

- **場所:** `apps/api/src/grants/grants.ts:24-27`、`apps/api/src/usage/state.ts:51-75`、`apps/api/src/admin/server.ts`（Task 5 の範囲）
- **何が起きるか:** `revokeGrant` は Grant だけを更新し `transitionUsageState(..., 'grant_revoked')` を呼ばない。Task 5 の管理APIには Grant 操作や手動 block/freeze のルートがなく、Task 7 も状態の閲覧・手動イベントを公開する管理APIを追加していない。Grantを取り消す経路が追加された際、状態行・コンテナ停止・通知は遅延し、ワーカーの毎時評価まで適用されない。また、既存の usage state が `active` のままでは、その間にアクセスや起動が通る可能性がある。
- **確度:** 高（対象コミットの関数・ルートを検索確認。後続Taskで追加される可能性は対象外）

### 中: 時間制限を超えた既存コンテナは meter が記録を足してから停止する

- **場所:** `apps/api/src/usage/runtime-hours.ts:90-119`
- **何が起きるか:** 各分の実行記録と利用カウンタ加算が先に行われ、上限到達後に `stopOwnerApps` が呼ばれる。上限直前に走っていたコンテナは次の meter 周期まで稼働し、その分を超過計上する。超過した分数・転送量ではなく、停止遅延分の稼働時間超過が起こり得る。
- **確度:** 高（処理順が明示されている）

### 低: エンベロープ解析は固定長を読み取るが、シリアライズ時に各フィールドの長さを検査しない

- **場所:** `packages/shared/src/idcrypt/envelope.ts:13-34`、`packages/shared/src/idcrypt/hybrid-kem.ts:78-86`
- **何が起きるか:** `serializeEnvelope` は公開鍵32/KEM暗号文1088/nonce12 の配列長を検査せず配置し、短い値では後続フィールドの位置がずれ、長い値では `Uint8Array.set` が例外になる。通常の暗号化関数は正しいプリミティブ出力を渡すため標準経路での不具合は確認できないが、外部Decryptor境界・将来の受信パーサーで不正長を早期に拒否する保証がない。
- **確度:** 中（未検証入力を受ける公開関数の挙動から）

## 問題を確認できなかった点

- **管理API認証:** `createAdminApp` は socket peer の Tailscale CIDR と `Tailscale-User-Login` に一致する有効 operator を要求し、セッション開始・完了以外は30分の昇格セッションを要求する。公開 `createApp` には `/admin` を登録せず、production では Tailscale 緩和設定を起動時拒否する。対象コード上、Tailscale外または昇格ログインなしで通常管理APIを使える経路は見つからなかった。
- **監査ハッシュ連鎖:** DBトリガーが advisory lock 下で連番・前ハッシュ・行ハッシュを設定し、UPDATE/DELETE/TRUNCATE を拒否、検証関数は欠番とハッシュ不整合を検出する。アプリ権限で迂回する経路は見つからなかった。DB所有者/superuserによるトリガー停止等はこのアプリ内制御の範囲外。
- **暗号の基本経路:** X25519とML-KEM-768の共有秘密をHKDF-SHA256で合成し、AES-256-GCMと版/uploadId/accountIdを含むAADを使用。公開鍵・秘密鍵長と画像サイズを確認しており、通常の暗号化/復号で明確な使い方誤りは見つからなかった。
